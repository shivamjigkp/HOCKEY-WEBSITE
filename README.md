# MMMUT Hockey Sports Platform A production-grade web platform for managing and showcasing university hockey — players, coaches, matches, results, live streams, galleries, news, and more, with a full Admin Dashboard for non-technical staff. Built per the standards defined in MASTER_PROMPT.md (the permanent source of truth for this project's architecture and conventions — read it before making changes). ## Tech Stack - **Frontend:** React 19, Vite, React Router DOM, Axios, Framer Motion, standard CSS3 - **Backend:** Supabase (PostgreSQL, Auth, Storage, Row Level Security) - **Deployment:** Vercel ## Getting Started
bash
# 1. Install dependencies
npm install

# 2. Copy the environment template and fill in your Supabase credentials
cp .env.example .env

# 3. Start the dev server
npm run dev

Root cause: StatsStrip's target value starts as the hardcoded default (e.g. 14 titles) on first render, then updates to the real value fetched from site_settings (e.g. 12) a moment later. The old hasAnimated ref never reset once set — so if the element was already scrolled into view before the Supabase fetch resolved, the counter would animate to the *default* value, mark itself "already animated," and then permanently ignore the real value arriving right after. Pure timing race: which number you saw depended on whether the fetch beat the scroll-into-view on that particular page load — hence "different every time." Fix: replaced the one-shot hasAnimated guard with hasIntersected (once the element has been seen, it stays eligible to re-animate) plus a controlsRef, so a later target change (defaults → real Supabase values) always triggers a fresh animation to the correct number instead of being silently dropped. Previous change: Fixed a duplicate/conflicting Admin Users implementation. Two separate systems had ended up managing profiles.role at once: SettingsManage.jsx had its own embedded AdminUsers component backed by services/adminUsers.js (from an earlier session, before the superadmin tier existed — its VALID_ROLES didn't even include 'superadmin'), while a newer, correctly-secured /admin/users (UsersManage.jsx + services/users.js) already existed, properly gated by ProtectedRoute's requireSuperAdmin and schema_phase22.sql's "Superadmins can update roles" RLS policy. Once schema_phase22 shipped and dropped the old "Admins can update roles" policy, the stale Settings-page version started hitting Cannot coerce the result to a single JSON object — a PostgREST error meaning .update().select().single() matched zero rows, because RLS was silently blocking the update for anyone who wasn't 'superadmin'. **Fix:** removed the duplicate — services/adminUsers.js deleted, SettingsManage.jsx's embedded user list replaced with a link to the real /admin/users. Only one system now touches roles. **Also renamed 'superadmin' to "Owner" — display-only.** The stored profiles.role value is still 'superadmin' (that's what the CHECK constraint, is_superadmin(), and every RLS policy that calls it expect — renaming the actual value would mean re-migrating the constraint, the function, and every existing row).
